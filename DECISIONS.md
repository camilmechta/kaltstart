# Decisions

| # | Decision | Reason | Options rejected |
|---|---|---|---|
| D1 | Portfolio first, continuation conditional on thresholds | A threshold fixed before the test shows a product approach | Portfolio only; real product from the start |
| D2 | Thresholds of 10 % human responses and 3 % positive responses | Above a generic mail, with enough volume to conclude | 5 %; 15 % |
| D3 | Requests limited to internship or part-time | A precise request makes the test comparable | Internship only; any type of request |
| D4 | One or two concrete examples written by the student | The only part that tells one student from another, without AI | Structured fields only; one example per role |
| D5 | 3 mails per company over 30 days, counted at generation | Protects the founder; the app always sees the generation | No limit; counter without blocking; counting at declared send |
| D6 | "Copy" buttons, limit of 5 pending mails | Matches real usage; pushes students to keep tracking up to date | `mailto:` button; hidden blind copy address |
| D7 | Named address only if published | Every address has a verifiable source; no bounces | Generic always; guessed address |
| D8 | Scraper thresholds at 70 % and 40 % | Checkpoint before investing in phases 3 to 5 | 50 %; 85 % |
| D9 | FastAPI for generation, GitHub Actions for the nightly job | Python must run on click; the nightly job needs no server | Queue in the database; templates rewritten in JavaScript |
| D10 | Mails presumed sent are excluded from the rates | It is unknown whether they left; they would distort the metric | Counting them as sent |
| D11 | Sign-up with an invitation code, no domain check | Simpler, no dependency on university mailboxes, control over who joins | Mandatory HSG address; open sign-up |
| D12 | Several template styles, style stored with each mail | The student picks the tone; the test compares styles | A single template |
| D13 | Public repository documents in English (README, PRD, DECISIONS, CHANGELOG, CLAUDE.md, code and commits) | Readable by European tech recruiters | French |
| D14 | Package `src/kaltstart/` instead of `src/ingestion/` directly | A single package name avoids import conflicts | One top-level package per component |
| D15 | Nightly synchronisation through `/changes` | It is the mechanism the API provides for synchronisation, and it also reports deletions | Re-reading `/rounds` every night |
| D16 | The sync watermark counts only successful `backfill` and `sync` runs; interrupted runs are recorded as failed | A successful details or reclean run must not hide a failed sync | Latest successful run of any command; interrupted runs left unrecorded |
| D17 | The details fetch stops and fails after 3 consecutive failures | Do not hammer a failing API; make systemic failure visible | Continue through every company; stop at the first failure |
| D18 | A repeated pagination cursor or an incomplete removed list is an error | A visible failure is better than silent data loss | Stop silently and record success |
| D19 | Weekly `backfill` every Sunday, in addition to the nightly `sync` | `/changes` reports added and removed rounds only, so edits to known rounds (such as an amount published later) would never arrive; a re-read costs about ten requests | Accept stale rounds; re-read `/rounds` every night |
| D20 | The design spec and the implementation plans are in English too, extending D13 to every file in the repository | The repository is public; a reader should not hit a language switch between the code and its design documents | Keep the spec and plans in French |
| D21 | A round missing a required field (date, identifier, page link, or the company's identifier, name, country or page link) is skipped and listed in the run summary, not stored | `/changes` can report a freshly created round before Tech.eu completes it (a null date was seen live on 2026-11-12); such a round cannot be placed in the 12-month window or stored under the schema. The weekly backfill picks it up within a week once it is complete, as long as it falls in the 12-month window | Use `createdAt` as the date; fail the run |
| D22 | Size bounds for rounds without a known stage set to 7 and 20 million euros (were 3 and 15) | Calibrated on the first load (2026-11-12, 832 rounds): median amounts are 2.0M for Pre-Seed, 4.3M for Seed, 12.0M for Series A and 31.8M for Series B, so each bound is a round figure between the medians of the two stages it separates. This assumes rounds without a known stage are distributed like the others, which is not verified. With 3M, more than half of Seed-sized rounds would have been classified medium | Keep 3 and 15; fit the bounds on the full distribution |
| D23 | Measure the contact scraper on 20 sites before building the nightly run and the database writes | The measurement is a checkpoint: if it fails, the method changes and anything built around it would be redone | Build the whole phase at once |
| D24 | The scraper reads the raw HTML of pages, without a browser | Fast, free and simple to run; the measurement shows how many sites need JavaScript | A real browser from the start; a browser as a fallback now |
| D25 | The scraper follows the home page's links by keyword, with fixed paths as a fallback | Sites use many names for the same page, in two languages; guessing paths mostly yields missing pages | Fixed paths only |
| D26 | Only addresses on the company's domain are kept; the others are counted as a failure cause | Protects against addresses of third parties; the count shows whether the rule costs too much | Keep any address found on the site |
| D27 | The scraper does not announce the project in its `User-Agent`, and does not imitate a browser | The project owner does not want the repository linked from site logs; pretending to be a browser would work around sites that refuse robots. Replaces "a tool name that identifies the project" in the design spec | A named bot with a link to the repository; a browser `User-Agent` |
| D28 | Detailed measurement results stay on the owner's machine; the repository holds only the sample and a summary without names or addresses | The repository is public; a file of founder names and addresses would be a ready-made contact list | Commit the full results |
| D29 | First verification pass by an assistant, then the owner confirms the finds and checks 5 companies independently | Keeps an independent human check at about half an hour of the owner's time | Owner checks all 20; no independent check |
| D30 | A measurement result within one company of a threshold is inconclusive, and 20 more companies are drawn | One company is 5 percentage points | Decide on 20 whatever the result |
| D31 | Redirects are followed by hand and each hop is checked before it is requested; social networks are never requested | The HTTP client followed redirects on its own, so a page redirecting to LinkedIn or a job board was fetched before the same-site check ran | Let the client follow redirects and drop foreign pages afterwards |
| D32 | A `robots.txt` that cannot be read (network error, 5xx) forbids the site; each host's own file is read; rules for the scraper's `User-Agent` are obeyed | Obeying `robots.txt` is a hard rule, and RFC 9309 asks to assume everything is disallowed when the file is unreachable. Replaces "unreadable means no restriction" | Treat an unreadable file as no restriction; check `*` rules only |
| D33 | Bare words are never read as an address; only the bracketed lower-case forms are | A heading such as "Jobs at Example.ch" became `jobs@example.ch`, an address nobody published | Accept `local at domain` when it is the whole text of an element |
| D34 | The parent of a site's host counts as the company's domain only for generic subdomains (`app.`, `shop.`) | For `startup.ethz.ch` or `startup.webflow.io`, the parent belongs to a university or a site builder | Trust any parent with two labels; add a public-suffix library |
| D35 | A personal address needs the founder's last name, or is exactly the first name; founder extraction binds each role to its nearest name and never takes a label as a name | `anna.schmidt@` was typed as the address of a founder called Anna Muster, and "Vertretungsberechtigte Person" was returned as a founder; a wrong name ends up in a mail | First or last name anywhere in the local part; first role of the block for every name in it |
| D36 | First Phase 2 measurement (2026-11-12, 20 Swiss companies, seed 2026): usable contact confirmed for 13 of 20 (65 %), inconclusive against the 70 % threshold; founder name confirmed for 1 of 20 (5 %), a clear fail against 40 %. The method for founder names must change before anything is built on it | Addresses: no wrong address, one missed (published on a second domain of the company); failures were 2 pages with almost no text, 2 without an address, 1 forbidden by `robots.txt`, 1 contact form only, 1 other domain only. Founders: 6 of the 7 lists reported contained entries that are not founders (job titles, organisations, the company's own name), and 3 founders were missed; a real founder was present in 6 of 20 lists. Two companies could not be fully verified (a certificate error on `robots.txt`, a bot check on a contact page). Verified by an assistant on all 20, with the owner's confirmation on 5 drawn at random | Treat 65 % as a pass; count a list with one real founder among several false names as a success |
| D37 | Founder extraction accepts a name only in a card, a "Name, role" line or a "role: Name" label, only when the role is held at this company, and never from prose | On the real team pages of the first measurement the name sits in its own block next to the role; reading "the name nearest to a role word" returned job titles, organisations and founders of other companies in 6 of 7 lists | Keep the nearest-name reading with longer stop lists; drop founder names from the product |
| D38 | Second Phase 2 measurement (2026-11-12, after D37): on 20 companies never seen before (seed 2027) and on the first 20 again, usable contact confirmed for 26 of 40 (65 %) and founder name for 12 of 40 (30 %, up from 5 %). Both thresholds are still missed; the scraper is reliable but does not see part of the pages | No wrong address in 40 companies. Six addresses missed, at least three because the page is built by JavaScript or refused the scraper. Founders: 6 lists contain a customer quoted in a testimonial on the home page, all their other names being right; 10 founders named on team or about pages were missed. The first pass of the first measurement had used a text fetch and wrongly reported no address on two JavaScript sites; corrected with a rendering browser. Verified by an assistant on all 40, with the owner's confirmation on 5 of each sample | Treat the improvement as a pass; decide on the first 20 alone |
| D39 | The usable-contact threshold is lowered from 70 % to 65 % | Decided by the project owner after two measurements at 65 %: without a browser the scraper cannot read pages built by JavaScript, which caps it near 67 %, and the owner prefers that to adding a browser now. Recorded as a threshold changed after seeing the results: 26 of 40 sits exactly on the new threshold, which the rules still read as inconclusive, so a third measurement on new companies decides | Keep 70 % and add a browser fallback; keep 70 % and stop |
| D40 | After the second measurement: a founder's name may sit one or two levels above its role; a card next to a quotation is a customer testimonial and is skipped; a role tied to another organisation's name before it or after a comma is dropped; addresses hidden by Cloudflare's email protection are decoded | The causes of every miss and every wrong list of the second measurement were read on the real pages: names in a neighbouring wrapper (3 companies), testimonial cards with the shape of team cards (5 companies), one address encoded by Cloudflare. No browser is added (D24 stands) | Stop reading the home page; add a browser |
| D41 | Third Phase 2 measurement (2026-11-12, after D40, 20 companies never seen before, seed 2028): usable contact confirmed for 14 of 20 (70 %) and founder name for 9 of 20 (45 %). Both are above their thresholds (65 % and 40 %) by one company, which the rules read as inconclusive; no code changes until more companies are measured | No wrong address in any of the three measurements. One founder list of ten was wrong (board members from investment firms); six founders were missed, three of them named only in a sentence, which the scraper does not read by design, one on a site that forbids robots. One address was missed, on that same site. Two companies could not be verified (an accelerator page in error, an untrusted certificate). Verified by an assistant on all 20, with the owner's confirmation on 5 | Declare a pass on 20 companies; keep changing the scraper before measuring again |
| D42 | Fourth Phase 2 measurement (2026-11-13, same code as the third, 20 more companies, seed 2029) and verdict on the 40 companies of the third and fourth samples: usable contact confirmed for 28 of 40 (70 %), a pass against 65 %; founder name confirmed for 14 of 40 (35 %), a fail against 40 %. The address part of the scraper is accepted; the founder part is not, and its method has reached its limit | The third sample alone gave 45 % for founders and the fourth 25 %: 20 companies were too few to conclude. No wrong address was found in any measurement; one company could not be verified (certificate error) and is counted as not confirmed. Founders: 14 found, 14 missed, 5 lists wrong; the misses and mistakes of the fourth sample each have a different cause (a "Founding Team" heading, a page in French only, a name in a hidden slide, a title taken from a blog post), so one more rule would gain a company or two at best. Four companies in 80 publish their address on a second domain of their own, which the scraper rejects. Verified by an assistant on all 40, with the owner's confirmation on 5 of each sample | Conclude on the third sample alone; keep adding rules for founders |
| D43 | The scraper reads people with their job title instead of founders | Reading a team card works; deciding who is a founder does not, and has no single cause left to fix (D42). For many companies a function head is the better person to write to | Keep adding founder rules; drop names altogether |
| D44 | Only leaders, heads and managers of five functions, and recruiters are kept | They decide on a hire, and it keeps personal data to people with an outward-facing role | Keep everyone on the team page |
| D45 | The person proposed follows the student's target role first, then the company's size | It answers the case where the head of a function is the right contact, and changes little at a company of ten. Replaces the size-only table of the design spec | Size first, as before |
| D46 | When the scraper finds nobody, the student completes the name, helped by a link to the team page and a search the student runs | Costs almost nothing, stores no scraped personal data, and makes the scraper's coverage a comfort instead of a gate | External paid data; address finders, which guess addresses; the Tech.eu API, whose founders field is empty |
| D47 | A name entered by a student is used for that student's mail only | No shared list built from unverified input | Share it with other students |
| D48 | Two criteria replace "name of a founder for 40 % of companies": accuracy at 90 %, blocking, and coverage at 40 %, a goal | A wrong name in a mail is worse than a missing one, and one figure hid the difference. Fixed before any measurement of the new code; the founder criterion had failed at 35 % | Coverage alone; no threshold |
| D49 | The verdict is taken on 40 new companies with frozen code | Twenty companies gave 45 % and then 25 % for the same code | Decide on 20 |
| D50 | One mail per person and per student | Protects the person, as the company cap protects the company | Company cap only |
| D51 | Before the first run of the people scraper: a name must come before its title; job openings, sentences, and cards under a section for advisors, a board, investors, openings or customers are skipped; a head word and a function must stand side by side; individual contributors' jobs carry no function; a company whose only address belongs to another person kept proposes that person | An independent review ran about 400 invented titles and layouts through the code and found that a job opening ("Head of Sales", then "Full Time") became a person called "Full Time", that "Lead Data Scientist" became a head of data, that "Produktionsleiter" became a head of product, and that a board president was kept. Two of the new rules were then found too broad on real pages kept locally (a team card classed "position", a name in a nested block) and narrowed | Run first and fix from the measurement |
| D52 | One tuning round on the 80 companies already seen, then the code is frozen: a title written above its name is read when the name is the title's next block and the title is not a heading; a few quoted words in a biography are not a testimonial (eight words or more are); a block with line breaks is read for its first line; a name may sit three levels above its title; text the page builder never shows is not read, while people behind a tab or a filter are; a card with a customer's logo and a statement is a testimonial; job titles in Italian and French are not names; a website that is a profile of the company on another organisation's site is not read (`not_own_site`) | On the 80 companies the people code reported 37 lists against about 33 for the founder code, and the testimonials and board members that made 9 lists wrong were gone. Reading the saved pages gave one cause each for 5 right lists that had vanished (D51 had made "name before title" too strict), 3 wrong lists (hidden text read as "Co-founder" for a whole team, a job title read as a name, a testimonial without quotation marks) and 2 wrong addresses (an accelerator's address proposed for a company listed there). These figures do not count for the verdict | A second round; re-running the 80 companies after the fixes |
